# Contributing

JameDesktopCommander treats commit, pull-request, and release metadata as part of the
engineering record. Repository policy is enforced by standard upstream tooling and GitHub
rulesets, not by informal text instructions.

## Commit messages

Commits follow Conventional Commits and are validated by Commitlint.

```text
type(scope): subject
```

Allowed types and scopes are defined in `commitlint.config.cjs`. A scope is mandatory and the
header is limited to 72 characters. Husky runs Commitlint through the `commit-msg` hook.

The repository intentionally does not require commit bodies. Husky enforces Conventional Commits
for new local commits, but Required CI does not reject an existing pull request solely because its
historical topic-branch commits predate JDC governance. `main` is squash-only: PR Governance
validates the pull-request title that becomes the final squash commit title, and the protected-branch
push validates that resulting commit with Commitlint. Pull-request bodies carry the detailed
rationale and verification evidence.

## Pull requests

Pull-request titles use the same Conventional Commits type/scope vocabulary and are validated
with `amannn/action-semantic-pull-request`.

Ordinary pull-request bodies contain exactly these level-two sections, in this order:

1. `What`
2. `Why`
3. `Testing`
4. `Related issues`

Every section must contain substantive content. Use GitHub closing keywords when applicable,
or write `None.` when no tracked issue exists.

Release Please pull requests are the only body-format exception. The exception applies only when
the pull request is created by the configured release bot, comes from this repository, and uses
the canonical Release Please branch. Their generated title must be
`chore(main): release <SemVer>`, and the Release Please body must remain generated and unedited.

## Local verification

Install the locked dependency graph and run the same primary gates used by CI:

```sh
npm ci
npm run lint:readme
npm run audit:runtime
npm run validate:tools
npm test
npm pack --dry-run
```

The pre-push Husky hook runs `npm run verify:push`.

## Branch policy

The protected default branch is squash-only. Direct pushes, deletion, and non-fast-forward
updates are blocked. Required status checks are evaluated against the latest base revision.

Every pull request into `main` requires:

- `PR Governance`;
- `Required CI`;
- resolved review conversations;
- CodeQL with no blocking high-or-higher security finding.

Published non-default branches are append-only. Force-pushes are blocked, except for the exact
Release Please automation branch because Release Please owns and updates that generated branch.

Source-controlled ruleset definitions live in `.github/rulesets/`. The remote GitHub rulesets
remain the enforcement authority.

## Squash merge contract

Squash merge is the only allowed merge method. Repository merge settings must use the pull-request
title as the squash commit title, and the squash commit message must remain blank. Pull-request
bodies retain the reviewed rationale and verification evidence in the pull request itself; they are
not copied into the protected-branch commit body.

Automation, agents, and maintainers must not override the squash commit message when completing a
merge. This preserves the repository setting `squashMergeCommitMessage: BLANK` and ensures the
protected-branch Commitlint gate validates the same governed Conventional Commit title that passed
PR Governance.

The initial fork migration may contain older topic-branch commits. They are reviewed and tested in
the pull request but enter `main` only through the single governed squash commit.

## Releases

Release Please is the only version, tag, and GitHub Release writer.

A dedicated GitHub App token is used so Release Please pull requests trigger the same required
governance and CI workflows as human pull requests. Configure these repository values before the
first release:

- variable `JDC_RELEASE_APP_CLIENT_ID`;
- secret `JDC_RELEASE_APP_PRIVATE_KEY`;
- variable `JDC_RELEASE_BOT_LOGIN` containing the exact GitHub App bot login.

Release Please owns `.release-please-manifest.json`, `package.json`, `package-lock.json`,
`server.json`, `src/version.ts`, the release pull request, the immutable `v*` tag, and the
GitHub Release. The release PR body is generated by Release Please and must not be rewritten into
the ordinary PR template.

npm, MCP Registry, and MCPB publication are intentionally disabled until the fork owns its final
package, registry, and bundle identities. The fork must never publish into upstream-owned
identities; `package.json` remains `private` until that namespace migration is complete.
